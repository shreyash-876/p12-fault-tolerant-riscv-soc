the code is linear, so the result does not depend on the data word.

## Notes on the numbers (all checked by enumeration)

- **Singles:** all 39 corrected by both codes.
- **Adjacent doubles (38):** Hsiao only detects them; the DAEC code corrects all 38. The project's Hsiao matrix has 119 forbidden
  4-cycles and only 12 distinct adjacent-pair syndromes, so it could not correct them even if the decoder tried.
- **Non-adjacent doubles (703):** Hsiao detects all of them. The DAEC code detects 300 and silently miscorrects 403 (57.3 %),
  because their syndrome equals that of an adjacent pair.
- **The paper's estimate is 379 / 703 = 53.9 %**, from Eq. (6), which counts bad 4-cycles. The exact count is 403 because some bad
  4-cycles contain two adjacent pairs, so one cycle makes two double-error patterns alias: 379 cycles give 403 aliasing patterns.
- **Triples (9139):** identical for both codes: 5452 miscorrected as a single error, 3687 detected. A triple has an odd-weight syndrome,
  so it can never match an (even-weight) adjacent-pair syndrome; and the number of miscorrected triples is 4 x (total 4-cycles) = 4 x 1363 = 5452
  for both codes, because both have 1363 four-cycles.
- **Hardware:** the syndrome generator has the same 96 two-input XORs and depth 4 as the Hsiao code. The extra cost is in the decoder:
  38 adjacent-pair comparators whose outputs are OR-ed into the flip signals of two neighbouring bits (paper, section 6, Fig. 5).
  This is measured, not assumed, in the Vivado sweep still to be done.
- **Fairness note:** my own quick search earlier reached 51 % miscorrection, lower than this paper's 57 %, but that search allowed columns of weight 5 and 7,
  which cost more XOR gates. The paper restricts the matrix to weight-1 and weight-3 columns to keep the logic as small as the Hsiao code's.
